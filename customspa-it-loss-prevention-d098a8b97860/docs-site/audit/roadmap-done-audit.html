    Metodo#

    Il documento non usa l'etichetta "DONE": assegna a ogni capacità (M01–M10) uno stato di completezza (Implemented, Partially implemented, Validation pending, Planned) e descrive cosa è già presente. Sono verificate tutte le funzionalità che il documento dichiara presenti / implementate / esistenti, comprese le parti dichiarate presenti nelle voci Partially implemented. Per le roadmap R01–R08 e N01–N06 sono verificate solo le affermazioni su ciò che esiste già. Lo stato dichiarato è indicato nella colonna "Voce".

    Per ogni voce: - Implementato: evidenze nel codice di ciò che esiste. - R – manca rispetto al requisito: ciò che il documento dichiara presente/funzionante non funziona o funziona solo in parte. Per le voci dichiarate parziali o incomplete, il requisito è la parte che il documento dichiara già presente. Quando non manca nulla rispetto al requisito è indicato Presente. - Q – valutazione di qualità: robustezza, sicurezza, architettura o completezza oltre quanto dichiarato. È una valutazione dell'auditor, non richiesta dal documento. Diversi di questi temi sono indicati dal documento stesso come attività "To complete for MVP" o come roadmap: restrizioni dati applicate dal server, workflow lookup, switch regole in ingestion, replay/recovery dei file, logging/audit, security hardening, revisione permessi, test e deployment automatizzati (R07), policy dashboard per regione/negozio/distretto e alert automatici (R06), SSO (R03), ulteriore validazione KNN (N05), controlli AI token/creatività (opzionali). - Esito: calcolato solo sulla colonna R. ✅ requisito soddisfatto · 🟡 requisito soddisfatto in parte · ❌ requisito non implementato.

    M01–M02 Integrazione dati e definizioni di business#

    Voce Implementato R – manca rispetto al requisito Q – valutazione di qualità Esito
    Ingestion SFTP/File System, CSV/XML/JSON
    Requisito (M01, stato dichiarato: parzialmente implementato): "Core imports […] are present"; "An administrator configures an SFTP or filesystem source and selects CSV, XML or JSON. The service processes the files, stores transaction records and adds source-file information."
    In parole semplici: il sistema deve caricare i dati delle transazioni da una cartella del server o da un archivio remoto di file (SFTP), nei formati CSV, XML e JSON.    		 Il sistema legge i file sia da una cartella del server sia da un archivio remoto protetto e riconosce i tre formati CSV, XML e JSON. Le impostazioni (da dove leggere, quando, con quale ricorrenza) si gestiscono dall'applicazione. A ogni esecuzione viene elaborato un solo formato di file. Presente Esiste anche un vecchio programma di caricamento separato che legge solo file XML da una cartella fissa scritta nel codice, carica le regole antifrode senza usarle e non tiene conto dei file già caricati. Ogni file XML viene trattato come un unico documento e i suoi attributi vengono salvati come testo, con il nome preceduto dal simbolo "@". ✅
    Schedulazione caricamenti
    Requisito (M01, stato dichiarato: parzialmente implementato): "Core imports, scheduling, source tracking and processed-file records are present"; tra le aree coinvolte: "scheduled loads".
    In parole semplici: deve essere possibile programmare i caricamenti dei dati a orari stabiliti.    		 Un servizio controlla ogni minuto se è arrivata l'ora di un caricamento programmato e lo avvia (con una tolleranza di un minuto). Il caricamento si può ripetere ogni giorno, ogni settimana o ogni mese. La programmazione si imposta da una schermata dedicata. L'opzione "una sola volta" non funziona: la schermata la propone, ed è anche la scelta predefinita, ma il servizio non esegue mai questo tipo di programmazione. La data scelta viene ignorata: conta solo l'ora. Il sistema ricorda l'ultima esecuzione solo finché resta acceso, quindi la protezione contro le esecuzioni doppie non è efficace. La ripetizione mensile scatta solo il primo giorno del mese ed è gestita dal server, ma non è selezionabile dalla schermata in uso. 🟡
    Tracciamento file sorgente
    Requisito (M01, stato dichiarato: parzialmente implementato): "source tracking […] present"; "The service […] adds source-file information".
    In parole semplici: per ogni dato caricato si deve sapere da quale file proviene.    		 Ogni record caricato riporta il nome del file di origine, la data e l'ora di elaborazione e il tipo di file. Presente — ✅
    Record file processati / load monitoring
    Requisito (M01, stato dichiarato: parzialmente implementato): "processed-file records are present"; "Processed-file records support load checking"; tra le aree coinvolte: "load monitoring". Il documento precisa: "Current duplicate checks depend on filenames".
    In parole semplici: deve esistere un registro dei file già caricati, che permetta di controllare i caricamenti ed evitare di caricare due volte lo stesso file.    		 Il sistema registra nel database ogni file caricato, con nome, numero di record e data. Un file con un nome già registrato viene saltato. Il monitoraggio dei caricamenti non è disponibile per gli utenti: il registro esiste solo nel database e non è consultabile da nessuna schermata né da nessun servizio dell'applicazione. Per verificarlo bisogna interrogare direttamente il database. Il riconoscimento dei doppioni si basa solo sul nome del file, senza altri controlli. Sull'archivio remoto, se nella cartella dei file elaborati esiste già un file con lo stesso nome, il nuovo file viene rinominato aggiungendo data e ora e inserito di nuovo. 🟡
    Move dei file SFTP in processed
    Requisito (M01, indicato come obiettivo): "The target workflow moves successfully handled SFTP files to a processed location and supports controlled reprocessing"; tra le attività da completare: "safe processed-file movement, partial-failure recovery and replay".
    In parole semplici: i file dell'archivio remoto già caricati devono essere spostati in una cartella "elaborati", e deve essere possibile ricaricarli in modo controllato.    		 Dopo il caricamento il file viene spostato nella cartella "processed"; in caso di errore nella cartella "failed". Se le cartelle non esistono vengono create. Lo spostamento è già operativo, anche se il documento lo presenta come obiettivo. Presente (lo spostamento; il ricaricamento controllato è indicato dal documento come attività da completare) Ogni file viene scaricato e letto due volte: la seconda volta viene ripreso dalla cartella "processed" per salvarne i dati. Se questo secondo passaggio fallisce, il file resta in "processed" senza che i dati siano stati salvati e viene ritentato al giro successivo. Non c'è una funzione per ricaricare un file a richiesta, né da schermata né da servizio; un file rimesso a mano nella cartella di partenza viene ignorato perché il suo nome risulta già caricato. ✅
    Streaming
    Requisito (M01, stato dichiarato: incompleto o da validare): "Streaming and robust recovery are incomplete or require validation"; tra le attività da completare: "finish or validate streaming".
    In parole semplici: i file devono poter essere elaborati "a flusso", cioè leggendoli un pezzo alla volta invece di caricarli interamente in memoria.    		 Nessuna implementazione. La funzione manca del tutto (non è parziale): ogni file dell'archivio remoto viene scaricato per intero in memoria e poi copiato in un file temporaneo prima di essere letto. — ❌
    Mapping Add/Rename/Remove
    Requisito (M02, stato dichiarato: implementato): "Mapping maintenance is implemented"; "Administrators add, rename or remove field mappings and define the fields presented for reporting."
    In parole semplici: gli amministratori devono poter gestire i "campi", cioè l'elenco delle informazioni utilizzabili nei report, con nome tecnico, nome da mostrare e tipo di dato.    		 Da una schermata dedicata si possono aggiungere, rinominare ed eliminare i campi. Quando si aggiunge un campo il sistema impedisce i doppioni di nome. Per ogni campo si impostano il nome da mostrare, il tipo di dato e se deve essere visibile nei report. Presente Quando si rinomina un campo non c'è il controllo dei doppioni. L'applicazione mostra solo i campi visibili, quindi un campo reso invisibile non può più essere ripristinato dalla schermata. Una funzione pensata per applicare i campi ai dati esiste, ma non viene mai usata. ✅
    Metadati lookup
    Requisito (M02, stato dichiarato: parziale): "Lookup-related metadata exists, but a complete lookup-table workflow remains outstanding."
    In parole semplici: devono esistere le informazioni di base per le tabelle di decodifica (lookup), che traducono codici in descrizioni leggibili (per esempio dal codice negozio al nome del negozio); il flusso di lavoro completo è dichiarato ancora da fare.    		 Esiste solo un'opzione "è un lookup" sui campi, attivabile dalla schermata dei campi. Il valore viene letto in un punto del costruttore di report ma non produce alcun effetto. Presente (corrisponde a quanto dichiarato) Non esistono tabelle, archivi o logica di decodifica: tutto il flusso di lavoro dei lookup va costruito da zero. ✅

    M03–M04 Reportistica e dashboard#

    Voce Implementato R – manca rispetto al requisito Q – valutazione di qualità Esito
    Workspaces create/rename/delete/search
    Requisito (M03, stato dichiarato: implementato, da validare): "Users create, rename, delete and search workspaces."
    In parole semplici: gli utenti devono poter creare, rinominare, eliminare e cercare le proprie aree di lavoro, in cui organizzano i report.    		 Tutte e quattro le operazioni sono disponibili da schermata e sono protette da un permesso specifico. La ricerca filtra l'elenco delle aree di lavoro. Presente La ricerca avviene solo sull'elenco già caricato nel browser. Al salvataggio l'applicazione mostra il messaggio di successo senza attendere la risposta del server, quindi lo mostra anche se il salvataggio non va a buon fine. ✅
    Tab add/rename/delete/duplicate
    Requisito (M03, stato dichiarato: implementato, da validare): "Within reports they add, rename, delete or duplicate tabs".
    In parole semplici: all'interno di un'area di lavoro l'utente deve poter aggiungere, rinominare, eliminare e duplicare le schede (tab), ciascuna con un proprio report.    		 Tutte le operazioni sono presenti; la duplicazione crea una copia completa e indipendente della scheda. Le schede vengono salvate insieme all'area di lavoro. Presente Le schede sono identificate solo dalla loro posizione (prima, seconda, …) e l'identificativo viene ricalcolato a ogni apertura. ✅
    Design/View
    Requisito (M03, stato dichiarato: implementato, da validare): "switch between design and view".
    In parole semplici: ogni report deve avere una modalità "Design" per costruirlo e una "View" per consultarne i risultati.    		 Il passaggio tra le due modalità funziona e la scelta viene salvata. In consultazione il report viene eseguito dal server e mostra i dati. Presente — ✅
    Espressioni
    Requisito (M03, stato dichiarato: implementato, da validare): "build expressions".
    In parole semplici: l'utente deve poter creare campi calcolati tramite una formula, cioè valori ottenuti a partire da altri campi.    		 Si possono definire campi calcolati con una formula; la formula viene salvata e il risultato compare nella tabella del report. Presente Le formule vengono calcolate nel browser con un meccanismo che esegue come codice il testo inserito: è una pratica rischiosa per la sicurezza. Il server non verifica né calcola le formule. I campi calcolati non compaiono nelle dashboard e non sono inclusi nelle esportazioni. ✅
    Prefix/Suffix
    Requisito (M03, stato dichiarato: implementato, da validare): "apply prefix/suffix formatting".
    In parole semplici: deve essere possibile mostrare un testo prima o dopo un valore, per esempio il simbolo "€" o "%".    		 Prefisso e suffisso vengono salvati e mostrati sia nella tabella del report sia nei riquadri tabellari delle dashboard. Nella tabella del report, quando le righe sono più di 200 e non ci sono regole di formattazione, prefisso e suffisso non vengono mostrati. Non sono inclusi nelle esportazioni, che contengono solo i valori puri. 🟡
    Conditional Formatting
    Requisito (M03, stato dichiarato: implementato, da validare): "Conditional formatting draws attention to selected results".
    In parole semplici: le celle devono potersi colorare automaticamente in base al loro valore, per mettere in evidenza i risultati che interessano.    		 Esiste una schermata per definire le regole, con 10 tipi di confronto tra cui scegliere. I colori vengono applicati nella tabella del report e nelle dashboard; una regola si può aggiungere anche dal menu che compare cliccando con il tasto destro su una cella. Funziona solo il confronto "uguale a", anche se ne vengono proposti 10. Le regole non vengono salvate: si perdono quando si salva e si riapre il report. Inoltre la schermata delle regole non mostra l'elenco dei campi tra cui scegliere, perché legge i nomi dei dati scritti con maiuscole/minuscole diverse da come li invia il server. — 🟡
    Heatmap
    Requisito (M03, stato dichiarato: implementato, da validare): "heatmaps show concentrations".
    In parole semplici: deve esistere una mappa di calore, cioè una griglia colorata che mostra a colpo d'occhio dove si concentrano i valori.    		 La mappa è presente, con legende, dettagli al passaggio del mouse e due modi di distribuire i colori (lineare e logaritmico). Applica la restrizione sui dati assegnata all'utente (per i limiti vedi "Restrizioni dati"). Presente La mappa potrebbe non aggiornarsi automaticamente quando cambia solo una parte delle sue impostazioni. ✅
    Heatmap Drilldown
    Requisito (M03, stato dichiarato: implementato, da validare): "drilldown exposes the supporting detail".
    In parole semplici: cliccando su una zona della mappa di calore si deve poter vedere il dettaglio dei dati che la compongono.    		 Il clic su una cella apre una nuova scheda "(Drilldown)" già filtrata sui due valori di quella cella. Presente Le date vengono convertite nell'ora locale del computer; l'effetto dipende dai dati. I filtri vengono aggiunti solo al primo livello delle condizioni. La nuova scheda non viene salvata automaticamente. ✅
    Dashboard chart/tabular/text add/edit/delete
    Requisito (M04, stato dichiarato: implementato, da validare): "Authorised users add, edit or delete charts, tables and explanatory text, arranging them into a dashboard."
    In parole semplici: gli utenti autorizzati devono poter comporre cruscotti (dashboard) con grafici, tabelle e testi, e poterli modificare o eliminare.    		 Si possono creare dashboard con riquadri di tipo grafico, tabella, testo e immagine, e modificarli o eliminarli. L'accesso è regolato da permessi e il server verifica i dati della dashboard. I grafici disponibili sono a barre, a linee, a torta, ad anello e radar. Un riquadro tabella ricorda solo il "numero" della scheda da cui prende i dati e la cerca in tutte le aree di lavoro. Poiché le schede sono numerate in base alla posizione, il riquadro può mostrare la scheda di un'altra area di lavoro, oppure una scheda diversa dopo un'eliminazione. I grafici delle dashboard non applicano né i filtri del report né la restrizione sui dati dell'utente. Non c'è un controllo specifico sulla configurazione di ciascun tipo di riquadro. Un file dell'interfaccia viene richiamato con maiuscole/minuscole diverse dal suo nome reale, cosa che funziona solo su sistemi che non distinguono maiuscole e minuscole (come Windows). Il riquadro immagine esiste ma non è citato dal documento. 🟡
    Condizioni nei report tabellari
    Requisito (M04, stato dichiarato: implementato, da validare): "Conditions on tabular reports narrow the information displayed."
    In parole semplici: nelle tabelle della dashboard si devono poter applicare dei filtri che restringono i dati mostrati.    		 Si possono costruire filtri anche complessi, combinando le condizioni con "E", "O" e "NESSUNA DI" e raggruppandole su più livelli. I filtri vengono applicati anche ai riquadri tabellari delle dashboard. I gruppi di condizioni su più livelli si perdono al salvataggio: il sistema salva solo un elenco semplice di condizioni. Le condizioni semplici vengono salvate correttamente. — 🟡

    M05–M06 Rilevazione eccezioni e analisi assistita#

    Voce Implementato R – manca rispetto al requisito Q – valutazione di qualità Esito
    Regole generiche
    Requisito (M05, stato dichiarato: nucleo implementato): "Generic rules […] are present"; "Users define business conditions and apply enabled rules to transaction records."
    In parole semplici: gli utenti devono poter definire regole antifrode e applicarle ai dati delle transazioni, usando solo le regole attive.    		 Esistono due tipi di regole. (a) Regole gestite dal server: si creano, modificano ed eliminano, e con il pulsante "Apply Rules" si applicano manualmente ai dati; vengono usate solo le regole attive e serve un permesso specifico. (b) Regole proposte dall'intelligenza artificiale ed eseguite nel browser. Le soglie di rilevazione vengono salvate. La modifica di una regola contiene un errore: salva il risultato in un punto sbagliato dei dati e cerca il campo con un nome sbagliato. Le regole del server sono semplici (uguaglianza, intervallo di valori, somma); per applicarle il sistema carica in memoria tutti i dati e li aggiorna uno alla volta. Le regole dell'intelligenza artificiale vengono eseguite come codice nel browser e non vengono salvate. 🟡
    Data Distance
    Requisito (M05, stato dichiarato: presente): "data-distance functionality [is] present"; "Data-distance views provide another way to explore records that differ from a selected comparison".
    In parole semplici: deve esistere un'analisi di "distanza" che, scelto un record, permetta di esplorare quanto gli altri record gli somigliano o se ne discostano.    		 Disponibile per chi ha il permesso di consultare i report. Per ogni record calcola un punteggio di somiglianza (per metà basato su quanti dei campi scelti si possono confrontare, per metà sulla distanza tra i valori) e mostra i 10 record più simili in una tabella e in un grafico radar. Presente (per la restrizione sui dati vedi "Restrizioni dati") I valori non vengono riportati su una scala comune, quindi i campi con numeri grandi pesano più degli altri nel calcolo. Le soglie sono fisse nel codice (almeno 3 campi confrontabili, 10 risultati). I risultati senza campo identificativo vengono scartati. Tutti i dati del periodo vengono caricati in memoria. Date ed elenchi di numeri o di valori sì/no non vengono gestiti. La validazione del metodo è rimandata alla roadmap (N05). ✅
    Esecuzione automatica regole in ingestion
    Requisito (M05, stato dichiarato: incompleto): "The MVP target includes a switch to apply rules automatically during ingestion"; "Automatic rule execution during ingestion remains incomplete".
    In parole semplici: deve esistere un interruttore che, se attivo, applica automaticamente le regole antifrode mentre i dati vengono caricati.    		 Le regole si possono applicare solo manualmente. Non esiste né l'interruttore né un meccanismo che esegua le regole durante il caricamento: il caricamento dei dati non richiama mai le regole. Il vecchio programma di caricamento le legge ma non le usa. Esiste una struttura predisposta per arricchire i dati durante il caricamento, ma nessuna regola concreta la utilizza. — ❌
    AI Report Generation
    Requisito (M06, stato dichiarato: parzialmente implementato): "Report-generation […] interfaces exist"; "The assisted-analysis functions propose report or query structures using the available fields."
    In parole semplici: l'intelligenza artificiale deve proporre report costruiti sui campi effettivamente disponibili.    		 Dalla barra degli strumenti si apre una finestra che chiede all'intelligenza artificiale di generare dei report; quelli proposti si aprono come schede nel costruttore di report. L'intelligenza artificiale non riceve l'elenco dei campi disponibili: la funzione non li inserisce nella richiesta, anche se la schermata li fornisce. Le proposte quindi non si basano sui campi reali. L'intelligenza artificiale (Ollama) viene chiamata direttamente dal browser all'indirizzo del computer locale: funziona solo se è installata sul computer dell'utente, non per utenti che si collegano da remoto, e non passa dal server. Gli errori non vengono mostrati all'utente. La schermata promette 25 report, ma la richiesta non indica quanti generarne. Esiste una seconda finestra "AI Report Generator" che non viene mai usata. 🟡
    AI NLQ
    Requisito (M06, stato dichiarato: parzialmente implementato): "[…] natural-language interfaces exist"; "A user describes the information they want, such as high-value refunds by store."
    In parole semplici: l'utente deve poter descrivere a parole cosa vuole vedere e ottenere dall'intelligenza artificiale una proposta di report.    		 La richiesta all'intelligenza artificiale include i campi disponibili con i loro nomi; la risposta (campi e filtri) si apre come nuova scheda nel costruttore di report. Presente Stesso limite della voce precedente: l'intelligenza artificiale è chiamata dal browser. Se qualcosa va storto l'utente non riceve alcun messaggio. Il server non verifica il risultato. I parametri dell'intelligenza artificiale sono fissi nel codice (il documento considera opzionali i controlli su questi parametri). ✅
    AI progress + batching
    Requisito (M06, stato dichiarato: parzialmente implementato): "Report-generation and natural-language interfaces exist, including progress and batching behavior"; "Progress feedback shows work taking place, while batching helps organise larger processing tasks."
    In parole semplici: le funzioni di intelligenza artificiale devono mostrare l'avanzamento del lavoro e suddividere le elaborazioni grandi in blocchi.    		 L'analisi antifrode con intelligenza artificiale lavora una pagina di dati alla volta (oppure una regola alla volta) e mostra una finestra con percentuale, numero di frodi trovate, tempo trascorso e un pulsante per interrompere. Nella finestra di generazione report e domande in linguaggio naturale, barra e testo di avanzamento non funzionano perché leggono informazioni che in quella parte dell'applicazione non esistono: si vede solo l'indicatore di attesa. Per le domande in linguaggio naturale non c'è lavorazione a blocchi. Il cronometro interno scrive solo nei messaggi tecnici del browser. 🟡

    M07–M09 Amministrazione, collaborazione e retention#

    Voce Implementato R – manca rispetto al requisito Q – valutazione di qualità Esito
    Login
    Requisito (M07, stato dichiarato: identità implementata): "Login […] exist[s]"; "Users sign in, work within their permitted functions".
    In parole semplici: gli utenti devono accedere con utente e password e lavorare solo con le funzioni a cui sono abilitati.    		 L'accesso funziona: verifica che l'utente sia attivo, controlla la password (conservata in forma non leggibile con un metodo che rispetta le raccomandazioni di sicurezza attuali; le password salvate con il metodo precedente vengono aggiornate al primo accesso) e rilascia un "gettone" di accesso che contiene i permessi e l'eventuale restrizione sui dati. Le pagine sono accessibili solo dopo il login. Presente Durante la creazione del gettone il server non attende il completamento di un'operazione; l'interfaccia compensa leggendo il risultato in un modo non standard. Quando l'accesso viene rifiutato (per esempio a gettone scaduto) l'interfaccia non ha una gestione centralizzata della situazione. ✅

    Gestione utenti + restrizione campo/valore
    Requisito (M07, stato dichiarato: identità implementata): "Administrators maintain users, roles and groups, and can associate a user with a field/value restriction."
    In parole semplici: gli amministratori devono gestire gli utenti e poter limitare ciò che un utente vede ai soli dati con un certo valore in un certo campo (per esempio i dati di un solo negozio).    		 Si possono creare, modificare ed eliminare utenti. La restrizione viene salvata quando si modifica un utente ed è inserita nel gettone di accesso. La restrizione non si può impostare quando si crea un utente: la schermata la invia ma il server la ignora. Una restrizione già assegnata non si può rimuovere: il sistema la aggiorna solo se sono compilati sia il campo sia il valore. Gli elenchi degli utenti restituiscono anche la password (in forma non leggibile) e i dati usati per proteggerla, che non dovrebbero uscire dal server. La data di registrazione viene sovrascritta a ogni modifica. Salvare un utente senza modifiche produce un errore. 🟡

    Requisito (M07, stato dichiarato: identità implementata; M08): "user/role management […] exist[s]"; "Administrators maintain users, roles and groups"; M08: "Users and groups provide the foundation for organising audiences."

Gruppi, ruoli e permessi si gestiscono completamente da schermata, ciascuno con i propri permessi di accesso. Un messaggio inviato a un gruppo viene recapitato a ciascun utente del gruppo.     Restrizioni dati
    Requisito (M07, stato dichiarato: parziale): "Data restrictions are partially implemented"; da completare: "Complete server-enforced data restrictions".
    In parole semplici: la restrizione campo/valore dell'utente deve limitare ciò che vede; il documento dichiara già presente una parte di questo meccanismo e indica come da completare il controllo lato server.    		 La restrizione viene aggiunta ai filtri dal browser, nella tabella del report, nella mappa di calore e nei riquadri tabellari delle dashboard. La restrizione è aggirabile dall'interfaccia: viene combinata con il tipo di collegamento scelto dall'utente per i filtri, quindi con "O" non limita più nulla e con "NESSUNA DI" viene addirittura invertita. L'analisi di somiglianza (Data Distance) la ignora e i grafici delle dashboard non la applicano. Il server non applica alcuna restrizione (parte che il documento dichiara da completare): non legge la restrizione dell'utente, esegue qualsiasi richiesta di dati che arrivi dal browser e conserva i risultati per 1 ora senza distinguere tra utenti. Un controllo di visibilità previsto sul server lascia sempre passare tutto. I riquadri tabellari delle dashboard non convertono correttamente i tipi di dato nei filtri. 🟡
    Notifiche
    Requisito (M08, stato dichiarato: implementato, da validare): "Basic notifications, read state and replies are implemented"; "Users receive or view relevant notifications, mark them read and use supported reply actions"; da validare: "recipients, visibility, read/reply behavior and removal".
    In parole semplici: gli utenti devono ricevere i messaggi a loro destinati, segnarli come letti, rispondere ed eliminarli.    		 Tutte le funzioni sono presenti, con l'icona a campanella nell'intestazione e la possibilità di inviare a singoli utenti o a gruppi. Ogni utente vede le notifiche di tutti, non solo le proprie: il sistema non filtra per destinatario. La campanella si carica solo per chi ha il permesso di gestione delle notifiche, e lo stesso permesso serve per segnare come letto, rispondere ed eliminare: un utente con il solo permesso di consultazione non vede le notifiche. Le notifiche non arrivano in tempo reale e non esistono notifiche automatiche (rinviate alla roadmap, R06/N02). Lo stato "letto" è unico per messaggio: per i gruppi viene creata una copia per ciascun utente, ma un messaggio inviato direttamente a più utenti ha un solo stato, condiviso da tutti. Il mittente viene indicato dal browser invece che dal server. Le notifiche indirizzate a un ruolo non vengono distribuite agli utenti di quel ruolo. 🟡
    Retention
    Requisito (M09, stato dichiarato: implementato in parte, da validare): "Retention setup exists"; "A configured retention period determines which older transactions expire […] the current 90-day default is a setting to review".
    In parole semplici: le transazioni più vecchie di un periodo configurato devono essere cancellate automaticamente; il valore predefinito attuale dichiarato è 90 giorni.    		 All'avvio il sistema imposta nel database la cancellazione automatica delle transazioni più vecchie del periodo configurato. Il periodo configurato è di 180 giorni; 90 giorni vengono usati solo se manca la configurazione. Il valore predefinito dichiarato (90 giorni) non corrisponde: sono configurati 180 giorni, anche nella copia di esempio del database. La cancellazione si basa su una data (BeginDateTime) che il caricamento dei dati non produce: nessuno dei 3.000 record della copia di esempio la contiene (hanno tutti un'altra data, TransactionDateTime). Con questi dati nessun record viene mai cancellato. Se la cancellazione automatica è già stata impostata in precedenza, una modifica del periodo non viene applicata. Nei file JSON le date vengono riconosciute come date solo se scritte in un formato speciale; altrimenti restano testo. Non c'è una schermata per gestire la retention. Il registro dei file caricati non viene mai ripulito. 🟡
