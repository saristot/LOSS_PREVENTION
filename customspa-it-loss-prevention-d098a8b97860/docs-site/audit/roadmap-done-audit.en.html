    Audit of items declared as implemented – Loss_Prevention_Business_Functionality_MVP_and_Roadmap.docx (LOSS_PREVENTION)#

    Requirements source: Loss_Prevention_Business_Functionality_MVP_and_Roadmap.docx ("MVP delivery and product roadmap", status at 13 October 2026). Codebase: customspa-it-loss-prevention-d098a8b97860 (commit baf7319). The audit is based only on what the source code shows, by reading the files directly. Build: - UI: vite build succeeds on Windows (with an eval warning in resultsGrid.vue). - Backend: NOT compiled, because the .NET SDK is not installed on the machine. - The repository contains no automated tests.

    Method#

    The document does not use a "DONE" label. Instead, it gives each capability (M01–M10) a completeness status (Implemented, Partially implemented, Validation pending or Planned) and describes what is already present.

    This audit checks every feature the document declares as present, implemented or existing. That includes the parts declared as present inside Partially implemented items. For roadmap items R01–R08 and N01–N06, only the statements about what already exists are checked. The "Item" column shows each item's declared status.

    Each item has these columns: - Implemented: code evidence of what exists. - R – missing vs. requirement: what the document declares as present or working but that does not work, or works only in part. For items declared as partial or incomplete, the requirement is the part the document says is already present. - Q – quality assessment: the auditor's view of robustness, security, architecture or completeness beyond what is declared. The document does not require these points. It already lists several of them itself, either as "To complete for MVP" activities or as roadmap items: - server-enforced data restrictions; - the lookup workflow; - the ingestion rule switch; - file replay and recovery; - logging/audit; - security hardening; - permissions review; - automated tests and deployment (R07); - region/store/district dashboard policies and automatic alerts (R06); - SSO (R03); - further KNN validation (N05); - AI token and creativity controls (optional). - Result: based only on the R column. - ✅ requirement met - 🟡 requirement partly met - ❌ requirement not implemented

    M07–M09 Administration, collaboration and retention#

    Item Implemented R – missing vs. requirement Q – quality assessment Result
    Login (M07 – identity implemented) LoginEndpoint.cs issues a JWT with permissions and the lock claims LockField/LockValue.
    UserService.LoginAsync checks IsActive and verifies the password with PBKDF2-SHA256 at 600k iterations; legacy 10k-iteration hashes are upgraded at login (PasswordHasher.cs:9-10).
    Front end: loginStore.ts, a router guard, and api.ts sending the Bearer token.    		 — CreateTokenAsync is not awaited (LoginEndpoint.cs:39); the frontend compensates by reading token.result.
    There is no 401 interceptor.    		 ✅
    Configurable session expiry (M07) JwtSettings.ExpiryHours in appsettings.json (=1, :33), applied in LoginEndpoint.cs:78 with AddHours(ExpiryHours). Logout is scheduled in loginStore.ts. — The JWT secret is hardcoded in appsettings.
    Expiry can be configured only in the file.    		 ✅
    Email password recovery (M07; R03 "already present") Forgot, Validate and Reset endpoints (anonymous). The token is SHA-256 hashed (PasswordResetService.cs:158), expires after 1 hour (:19) and is single-use. The email link is {FrontendUrl}/reset-password?token= (EmailService.cs:29). UI and route exist. The server enforces at least 8 characters (ResetPasswordEndpoint). — SMTP host/port come from appsettings (localhost:25), with EnableSsl=false hardcoded (EmailService.cs:64) and UseDefaultCredentials=true, so a relay is required.
    The token lifetime is hardcoded, and token use is not atomic.
    The UI does not enforce a minimum length.
    An inactive user gets a different response (ForgotPasswordEndpoint.cs:45), which reveals that the account exists.    		 ✅
    User management and field/value restriction (M07 – "administrators maintain users … associate a user with a field/value restriction") User CRUD. The lock is saved on update (UserService.cs:100-104) and added to the JWT (LoginEndpoint.cs:65-68). The lock cannot be set at creation: the UI sends lockField/lockValue (users.vue:268-280), but CreateUserRequest and its endpoint ignore them.
    The lock cannot be removed: it is updated only when both values are non-empty (UserService.cs:100).    		 GetUsers (GetUsersEndpoint.cs:36) and CreateUser return PasswordHash and PasswordSalt.
    RegistrationDate is overwritten on every update.
    An update with no changes returns 400.    		 🟡
    Roles and groups (M07; M08 "users and groups provide the foundation for organising audiences") Groups, Roles and Permissions CRUD and UI (CAN_MANAGE_GROUPS/CAN_VIEW_GROUPS, CAN_ROLE, CAN_PERMISSION). Group sends are expanded into one notification per user (groupStore.ts:40-49, notificationStore.ts:116-130). — The group-to-user expansion happens only in the frontend; the backend does not resolve groups or roles.
    The router checks only authentication (router/index.ts:65); permissions are checked only in the menus.    		 ✅
    Data restrictions (M07 – declared partial) The lock is applied client-side through generateSimpleMatch (queryUtils.ts:165-174) in resultsGrid.vue, toolbar.vue (heatmap) and tabularBlock.vue. The lock is combined using the root group's operator (queryUtils.ts:174): with an OR root it does not restrict, and with NOR it is negated, so a user can bypass it from the UI.
    Distance ignores the lock.
    Dashboard charts do not apply it (chartblock.vue has no $match).    		 There is no server-side enforcement, which the document lists as still to complete:
    • no backend code reads the lock claims;
    • GetReportDataEndpoint runs any pipeline the client sends (:66-71);
    • the 1-hour cache is not per user;
    • the visibility filter in ReportDataservice is always true.
    tabularBlock passes empty mappings, so no type conversion happens.    		 🟡
    Notifications: send, read state, replies and removal (M08 – implemented) Create, List, MarkAsRead, Reply and Delete endpoints. Bell icon in App.vue. Notifications can be sent to users and groups. Every user sees every notification: ListNotificationsEndpoint uses Filter.Empty, with no recipient filter.
    The bell loads notifications only for users with CAN_MANAGE_NOTIFICATIONS (App.vue:165/172, notificationStore.ts:70-73), and MarkAsRead, Reply and Delete require the same permission. As a result, a user with only CAN_VIEW_NOTIFICATIONS sees no notifications.    		 No push, polling or automatic notifications (deferred to R06/N02).
    IsRead is stored once per notification. Group sends create one notification per user, but a direct send to several users creates one shared notification, so its read state is shared.
    From is supplied by the client.
    Notifications with toType 'role' are never resolved to recipients.    		 🟡
    Retention (M09 – implemented in part; "configured retention period determines which older transactions expire … current 90-day default") The API creates the TTL index ttl_BeginDateTime at startup (DatabaseInitializationService.cs:97-101). Retention comes from appsettings DataRetention:TransactionRetentionDays = 180 (:8-9); 90 is only the fallback (DatabaseInitializationService.cs:23). The declared 90-day default does not match: 180 days are configured. The repository dump agrees: ReportData.metadata.json has expireAfterSeconds 15552000, i.e. 180 days.
    The TTL is on the BeginDateTime field, which ingestion never produces and which appears nowhere else in the code. None of the 3,000 documents in the ReportData.bson dump has BeginDateTime; they all have TransactionDateTime. With this data, no document ever expires.    		 If the TTL index already exists, a retention change is not applied (:64-71).
    JSON dates become BSON Dates only in Extended JSON form ({"$date": …}); plain date strings stay strings.
    There is no retention UI.
    ProcessedFiles has no TTL.    		 🟡
