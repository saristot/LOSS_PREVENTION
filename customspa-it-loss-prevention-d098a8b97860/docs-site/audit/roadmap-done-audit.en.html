    Audit of items declared as implemented – Loss_Prevention_Business_Functionality_MVP_and_Roadmap.docx (LOSS_PREVENTION)#

    Requirements source: Loss_Prevention_Business_Functionality_MVP_and_Roadmap.docx ("MVP delivery and product roadmap", status at 13 October 2026). Codebase: customspa-it-loss-prevention-d098a8b97860 (commit baf7319). The audit is based only on what the source code shows, by reading the files directly. Build: - UI: vite build succeeds on Windows (with an eval warning in resultsGrid.vue). - Backend: NOT compiled, because the .NET SDK is not installed on the machine. - The repository contains no automated tests.

    Method#

    The document does not use a "DONE" label. Instead, it gives each capability (M01–M10) a completeness status (Implemented, Partially implemented, Validation pending or Planned) and describes what is already present.

    This audit checks every feature the document declares as present, implemented or existing. That includes the parts declared as present inside Partially implemented items. For roadmap items R01–R08 and N01–N06, only the statements about what already exists are checked. The "Item" column shows each item's declared status.

    Each item has these columns: - Implemented: code evidence of what exists. - R – missing vs. requirement: what the document declares as present or working but that does not work, or works only in part. For items declared as partial or incomplete, the requirement is the part the document says is already present. When nothing is missing against the requirement, the column says Present. - Q – quality assessment: the auditor's view of robustness, security, architecture or completeness beyond what is declared. The document does not require these points. It already lists several of them itself, either as "To complete for MVP" activities or as roadmap items: - server-enforced data restrictions; - the lookup workflow; - the ingestion rule switch; - file replay and recovery; - logging/audit; - security hardening; - permissions review; - automated tests and deployment (R07); - region/store/district dashboard policies and automatic alerts (R06); - SSO (R03); - further KNN validation (N05); - AI token and creativity controls (optional). - Result: based only on the R column. - ✅ requirement met - 🟡 requirement partly met - ❌ requirement not implemented

    M01–M02 Data integration and business definitions#

    Item Implemented R – missing vs. requirement Q – quality assessment Result
    SFTP/file-system ingestion, CSV/XML/JSON
    Requirement (M01, declared status: partially implemented): "Core imports […] are present"; "An administrator configures an SFTP or filesystem source and selects CSV, XML or JSON. The service processes the files, stores transaction records and adds source-file information."
    In plain words: the system must load transaction data from a server folder or from a remote file store (SFTP), in CSV, XML and JSON formats.    		 The system reads files both from a server folder and from a secure remote file store, and it recognises the three formats CSV, XML and JSON. The settings (where to read from, when, how often) are managed from within the application. Each run processes one file format only. Present There is also an old, separate loading program that reads only XML files from a fixed folder written into the code, loads the anti-fraud rules without using them, and does not take already-loaded files into account. Each XML file is treated as a single document and its attributes are saved as text, with the name preceded by the "@" symbol. ✅
    Load scheduling
    Requirement (M01, declared status: partially implemented): "Core imports, scheduling, source tracking and processed-file records are present"; among the areas involved: "scheduled loads".
    In plain words: it must be possible to schedule data loads at set times.    		 A service checks every minute whether a scheduled load is due and starts it (with a one-minute tolerance). A load can repeat daily, weekly or monthly. The schedule is set up on a dedicated screen. The "one-time" option does not work: the screen offers it, and it is even the default choice, but the service never runs this type of schedule. The chosen date is ignored: only the time counts. The system remembers the last run only while it stays switched on, so the protection against duplicate runs is not effective. The monthly repetition runs only on the first day of the month; the server supports it, but it cannot be selected on the screen currently in use. 🟡
    Source-file tracking
    Requirement (M01, declared status: partially implemented): "source tracking […] present"; "The service […] adds source-file information".
    In plain words: for every loaded record it must be possible to know which file it came from.    		 Every loaded record carries the name of its source file, the processing date and time, and the file type. Present — ✅
    Processed-file records and load monitoring
    Requirement (M01, declared status: partially implemented): "processed-file records are present"; "Processed-file records support load checking"; among the areas involved: "load monitoring". The document adds: "Current duplicate checks depend on filenames".
    In plain words: there must be a log of the files already loaded, so that loads can be checked and the same file is not loaded twice.    		 The system records every loaded file in the database, with its name, number of records and date. A file whose name is already recorded is skipped. Load monitoring is not available to users: the log exists only in the database and cannot be viewed from any screen or any service of the application. Checking it requires querying the database directly. Duplicates are recognised only by file name, with no other checks. On the remote file store, if a file with the same name already exists in the processed-files folder, the new file is renamed by adding date and time and is inserted again. 🟡
    Moving SFTP files to processed
    Requirement (M01, stated as the target): "The target workflow moves successfully handled SFTP files to a processed location and supports controlled reprocessing"; among the activities to complete: "safe processed-file movement, partial-failure recovery and replay".
    In plain words: files from the remote store that have been loaded must be moved to a "processed" folder, and it must be possible to reload them in a controlled way.    		 After loading, the file is moved to the "processed" folder; on error, to the "failed" folder. The folders are created if they do not exist. The move is already working, even though the document presents it as a target. Present (the move; controlled reloading is listed by the document as an activity still to complete) Each file is downloaded and read twice: the second time it is taken again from the "processed" folder to save its data. If this second step fails, the file stays in "processed" without its data being saved, and it is retried on the next run. There is no function to reload a file on request, neither from a screen nor from a service; a file put back by hand into the source folder is ignored because its name is already recorded as loaded. ✅
    Streaming
    Requirement (M01, declared status: incomplete or to be validated): "Streaming and robust recovery are incomplete or require validation"; among the activities to complete: "finish or validate streaming".
    In plain words: files must be processed as a "stream", that is, read one piece at a time instead of being loaded entirely into memory.    		 No implementation. The feature is missing entirely (not partial): every file from the remote store is downloaded in full into memory and then copied to a temporary file before being read. — ❌
    Mapping add, rename and remove
    Requirement (M02, declared status: implemented): "Mapping maintenance is implemented"; "Administrators add, rename or remove field mappings and define the fields presented for reporting."
    In plain words: administrators must be able to manage the "fields", that is, the list of information that can be used in reports, with technical name, display name and data type.    		 From a dedicated screen, fields can be added, renamed and deleted. When a field is added, the system prevents duplicate names. For each field you set the display name, the data type and whether it is visible in reports. Present When a field is renamed there is no duplicate check. The application shows only visible fields, so a field made invisible can no longer be restored from the screen. A function meant to apply the fields to the data exists but is never used. ✅
    Lookup metadata
    Requirement (M02, declared status: partial): "Lookup-related metadata exists, but a complete lookup-table workflow remains outstanding."
    In plain words: the basic information for lookup tables must exist; lookup tables translate codes into readable descriptions (for example from store code to store name). The complete workflow is declared as still to be done.    		 There is only an "is a lookup" option on fields, which can be switched on from the fields screen. The value is read in one place of the report builder but has no effect. Present (matches what is declared) There are no lookup tables, stores or lookup logic: the whole lookup workflow has to be built from scratch. ✅

    M03–M04 Reporting and dashboards#

    Item Implemented R – missing vs. requirement Q – quality assessment Result
    Workspace create, rename, delete and search
    Requirement (M03, declared status: implemented, validation pending): "Users create, rename, delete and search workspaces."
    In plain words: users must be able to create, rename, delete and search their workspaces, where they organise their reports.    		 All four operations are available on screen and protected by a specific permission. Search filters the list of workspaces. Present Search works only on the list already loaded in the browser. When saving, the application shows the success message without waiting for the server's answer, so it shows it even when saving fails. ✅
    Tab add, rename, delete and duplicate
    Requirement (M03, declared status: implemented, validation pending): "Within reports they add, rename, delete or duplicate tabs".
    In plain words: inside a workspace the user must be able to add, rename, delete and duplicate tabs, each holding its own report.    		 All operations are available; duplicating creates a complete, independent copy of the tab. Tabs are saved together with the workspace. Present Tabs are identified only by their position (first, second, …) and the identifier is recalculated every time the workspace is opened. ✅
    Design/View
    Requirement (M03, declared status: implemented, validation pending): "switch between design and view".
    In plain words: each report must have a "Design" mode to build it and a "View" mode to look at its results.    		 Switching between the two modes works and the choice is saved. In view mode the report is run by the server and shows the data. Present — ✅
    Expressions
    Requirement (M03, declared status: implemented, validation pending): "build expressions".
    In plain words: users must be able to create calculated fields through a formula, that is, values obtained from other fields.    		 Calculated fields can be defined with a formula; the formula is saved and the result appears in the report table. Present Formulas are calculated in the browser with a mechanism that runs the entered text as code: this is a risky practice for security. The server neither checks nor calculates the formulas. Calculated fields do not appear in dashboards and are not included in exports. ✅
    Prefix/Suffix
    Requirement (M03, declared status: implemented, validation pending): "apply prefix/suffix formatting".
    In plain words: it must be possible to show text before or after a value, for example the "€" or "%" symbol.    		 Prefix and suffix are saved and shown both in the report table and in the table blocks of dashboards. In the report table, when there are more than 200 rows and no formatting rules, prefix and suffix are not shown. They are not included in exports, which contain only the raw values. 🟡
    Conditional formatting
    Requirement (M03, declared status: implemented, validation pending): "Conditional formatting draws attention to selected results".
    In plain words: cells must be coloured automatically according to their value, to highlight the results of interest.    		 There is a screen to define the rules, with 10 types of comparison to choose from. Colours are applied in the report table and in dashboards; a rule can also be added from the menu that appears when right-clicking a cell. Only the "equal to" comparison works, although 10 are offered. Rules are not saved: they are lost when the report is saved and reopened. In addition, the rules screen does not show the list of fields to choose from, because it reads the data names with a different upper/lower case from the one the server sends. — 🟡
    Heatmap
    Requirement (M03, declared status: implemented, validation pending): "heatmaps show concentrations".
    In plain words: there must be a heatmap, that is, a coloured grid that shows at a glance where values are concentrated.    		 The heatmap is available, with legends, details on mouse-over and two ways of spreading the colours (linear and logarithmic). It applies the data restriction assigned to the user (for its limits see "Data restrictions"). Present The map may not refresh automatically when only part of its settings changes. ✅
    Heatmap drilldown
    Requirement (M03, declared status: implemented, validation pending): "drilldown exposes the supporting detail".
    In plain words: clicking an area of the heatmap must show the detailed data behind it.    		 Clicking a cell opens a new "(Drilldown)" tab already filtered on the two values of that cell. Present Dates are converted to the computer's local time; the effect depends on the data. Filters are added only at the first level of the conditions. The new tab is not saved automatically. ✅
    Dashboard chart, tabular and text blocks: add, edit and delete
    Requirement (M04, declared status: implemented, validation pending): "Authorised users add, edit or delete charts, tables and explanatory text, arranging them into a dashboard."
    In plain words: authorised users must be able to build dashboards from charts, tables and texts, and to edit or delete them.    		 Dashboards can be created with chart, table, text and image blocks, which can be edited or deleted. Access is governed by permissions and the server checks the dashboard data. Available charts are bar, line, pie, doughnut and radar. A table block remembers only the "number" of the tab it takes its data from and looks for it across all workspaces. Since tabs are numbered by position, the block may show a tab from another workspace, or a different tab after a deletion. Dashboard charts apply neither the report filters nor the user's data restriction. There is no specific check of the configuration of each block type. One interface file is referenced with a different upper/lower case from its real name, which works only on systems that do not distinguish upper and lower case (such as Windows). The image block exists but is not mentioned in the document. 🟡
    Conditions on tabular reports
    Requirement (M04, declared status: implemented, validation pending): "Conditions on tabular reports narrow the information displayed."
    In plain words: it must be possible to apply filters to dashboard tables that narrow the data shown.    		 Even complex filters can be built, combining conditions with "AND", "OR" and "NONE OF" and grouping them on several levels. Filters are also applied to the table blocks of dashboards. Groups of conditions on several levels are lost when saving: the system saves only a simple list of conditions. Simple conditions are saved correctly. — 🟡

    M05–M06 Exception detection and assisted analysis#

    Item Implemented R – missing vs. requirement Q – quality assessment Result
    Generic rules: define rules and apply the enabled ones
    Requirement (M05, declared status: core implemented): "Generic rules […] are present"; "Users define business conditions and apply enabled rules to transaction records."
    In plain words: users must be able to define anti-fraud rules and apply them to transaction data, using only the active rules.    		 There are two kinds of rules. (a) Rules managed by the server: they can be created, edited and deleted, and the "Apply Rules" button applies them manually to the data; only active rules are used and a specific permission is required. (b) Rules proposed by artificial intelligence and run in the browser. Detection thresholds are saved. Editing a rule contains a bug: it saves the result in the wrong place in the data and looks for the field under the wrong name. Server rules are simple (equality, value range, sum); to apply them the system loads all the data into memory and updates records one by one. Artificial-intelligence rules are run as code in the browser and are not saved. 🟡
    Data distance
    Requirement (M05, declared status: present): "data-distance functionality [is] present"; "Data-distance views provide another way to explore records that differ from a selected comparison".
    In plain words: there must be a "distance" analysis that, once a record is chosen, lets users explore how much other records resemble it or differ from it.    		 Available to users with permission to view reports. For each record it calculates a similarity score (half based on how many of the chosen fields can be compared, half on the distance between values) and shows the 10 most similar records in a table and in a radar chart. Present (for the data restriction see "Data restrictions") Values are not brought onto a common scale, so fields with large numbers weigh more than others in the calculation. Thresholds are fixed in the code (at least 3 comparable fields, 10 results). Results without an identifying field are discarded. All data for the period is loaded into memory. Dates and lists of numbers or yes/no values are not handled. Validation of the method is deferred to the roadmap (N05). ✅
    Automatic rule execution during ingestion
    Requirement (M05, declared status: incomplete): "The MVP target includes a switch to apply rules automatically during ingestion"; "Automatic rule execution during ingestion remains incomplete".
    In plain words: there must be a switch that, when on, automatically applies the anti-fraud rules while data is being loaded.    		 Rules can only be applied manually. Neither the switch nor any mechanism that runs the rules during loading exists: data loading never calls the rules. The old loading program reads them but does not use them. There is a structure prepared for enriching data during loading, but no actual rule uses it. — ❌
    AI report generation
    Requirement (M06, declared status: partially implemented): "Report-generation […] interfaces exist"; "The assisted-analysis functions propose report or query structures using the available fields."
    In plain words: artificial intelligence must propose reports built on the fields actually available.    		 From the toolbar, a window opens that asks artificial intelligence to generate reports; the proposed ones open as tabs in the report builder. Artificial intelligence does not receive the list of available fields: the function does not include them in the request, even though the screen provides them. The proposals are therefore not based on the real fields. Artificial intelligence (Ollama) is called directly from the browser at the local computer's address: it works only if it is installed on the user's own computer, not for users connecting remotely, and it does not go through the server. Errors are not shown to the user. The screen promises 25 reports, but the request does not say how many to generate. There is a second "AI Report Generator" window that is never used. 🟡
    AI NLQ
    Requirement (M06, declared status: partially implemented): "[…] natural-language interfaces exist"; "A user describes the information they want, such as high-value refunds by store."
    In plain words: users must be able to describe in words what they want to see and get a report proposal from artificial intelligence.    		 The request to artificial intelligence includes the available fields and their names; the answer (fields and filters) opens as a new tab in the report builder. Present Same limit as the previous item: artificial intelligence is called from the browser. If something goes wrong the user gets no message. The server does not check the result. The artificial-intelligence settings are fixed in the code (the document considers controls over these settings optional). ✅
    AI progress and batching
    Requirement (M06, declared status: partially implemented): "Report-generation and natural-language interfaces exist, including progress and batching behavior"; "Progress feedback shows work taking place, while batching helps organise larger processing tasks."
    In plain words: artificial-intelligence functions must show the progress of the work and split large processing tasks into batches.    		 The anti-fraud analysis with artificial intelligence works one page of data at a time (or one rule at a time) and shows a window with percentage, number of frauds found, elapsed time and a stop button. In the report-generation and natural-language-question window, the progress bar and text do not work because they read information that does not exist in that part of the application: only the waiting indicator is shown. Natural-language questions are not processed in batches. The internal timer writes only to the browser's technical messages. 🟡

    M07–M09 Administration, collaboration and retention#

    Item Implemented R – missing vs. requirement Q – quality assessment Result
    Login
    Requirement (M07, declared status: identity implemented): "Login […] exist[s]"; "Users sign in, work within their permitted functions".
    In plain words: users must sign in with username and password and work only with the functions they are allowed to use.    		 Sign-in works: it checks that the user is active, verifies the password (stored in unreadable form with a method that follows current security recommendations; passwords stored with the previous method are upgraded at the first sign-in) and issues an access "token" containing the permissions and any data restriction. Pages are accessible only after login. Present When creating the token, the server does not wait for one operation to complete; the interface compensates by reading the result in a non-standard way. When access is refused (for example when the token has expired), the interface has no central handling of the situation. ✅
    Configurable session expiry
    Requirement (M07, declared status: identity implemented): "configurable session expiry […] exist[s]".
    In plain words: a work session must expire after a configurable time, after which the user has to sign in again.    		 The duration is set in the configuration file (currently 1 hour); when it expires the user is signed out automatically. Present The secret key used to guarantee that sign-ins are genuine is written in plain text in the configuration file. The duration can be changed only in the file, not from a screen. ✅
    Email password recovery
    Requirement (M07, declared status: identity implemented; R03): "email password recovery exist[s]"; "recover access through the password-reset journey"; R03: "Email-based forgot-password capability is already present".
    In plain words: anyone who forgets their password must be able to reset it through a link received by email.    		 The user requests recovery, receives by email a link valid for 1 hour that can be used only once, and chooses the new password on a dedicated page. The code contained in the link is stored in unreadable form. The server requires a password of at least 8 characters. Present Email sending is configured towards a local mail server, without an encrypted connection and with the system's default credentials, so a prepared relay mail server is needed. The link duration is fixed in the code. The link is not protected against two simultaneous uses. The screen does not state the minimum password length. For a deactivated user the system answers differently, thereby revealing that the account exists. ✅
    User management and field/value restriction
    Requirement (M07, declared status: identity implemented): "Administrators maintain users, roles and groups, and can associate a user with a field/value restriction."
    In plain words: administrators must manage users and be able to limit what a user sees to the data with a certain value in a certain field (for example the data of a single store).    		 Users can be created, edited and deleted. The restriction is saved when a user is edited and is included in the access token. The restriction cannot be set when a user is created: the screen sends it but the server ignores it. A restriction already assigned cannot be removed: the system updates it only when both the field and the value are filled in. User lists also return the password (in unreadable form) and the data used to protect it, which should not leave the server. The registration date is overwritten at every edit. Saving a user with no changes produces an error. 🟡
    Roles and groups
    Requirement (M07, declared status: identity implemented; M08): "user/role management […] exist[s]"; "Administrators maintain users, roles and groups"; M08: "Users and groups provide the foundation for organising audiences."
    In plain words: there must be roles, groups and permissions that determine who can do what and to whom messages are sent.    		 Groups, roles and permissions are fully managed from screens, each with its own access permissions. A message sent to a group is delivered to each user in the group. Present Delivery to group members is done by the browser: the server does not know which users belong to which groups and roles. Pages check only that the user has signed in; permissions are used only to hide menu items, not to prevent a page from being opened directly. ✅
    Data restrictions
    Requirement (M07, declared status: partial): "Data restrictions are partially implemented"; to complete: "Complete server-enforced data restrictions".
    In plain words: the user's field/value restriction must limit what the user sees; the document declares part of this mechanism as already present and lists server-side enforcement as still to complete.    		 The browser adds the restriction to the filters in the report table, the heatmap and the table blocks of dashboards. The restriction can be bypassed from the interface: it is combined with the type of link the user chooses for the filters, so with "OR" it no longer limits anything and with "NONE OF" it is even reversed. The similarity analysis (Data distance) ignores it and dashboard charts do not apply it. The server applies no restriction at all (the part the document declares still to complete): it does not read the user's restriction, runs any data request coming from the browser and keeps results for 1 hour without distinguishing between users. A visibility check planned on the server always lets everything through. Dashboard table blocks do not convert data types correctly in filters. 🟡
    Notifications: send, read state, replies and removal
    Requirement (M08, declared status: implemented, validation pending): "Basic notifications, read state and replies are implemented"; "Users receive or view relevant notifications, mark them read and use supported reply actions"; to validate: "recipients, visibility, read/reply behavior and removal".
    In plain words: users must receive the messages addressed to them, mark them as read, reply and delete them.    		 All functions are available, with a bell icon in the header and the option to send to individual users or to groups. Every user sees everyone's notifications, not just their own: the system does not filter by recipient. The bell loads only for users with the notification-management permission, and the same permission is required to mark as read, reply and delete: a user with only the viewing permission does not see notifications. Notifications do not arrive in real time and there are no automatic notifications (deferred to the roadmap, R06/N02). The "read" state is one per message: for groups a copy is created for each user, but a message sent directly to several users has a single state shared by all of them. The sender is set by the browser instead of the server. Notifications addressed to a role are not delivered to the users of that role. 🟡
    Retention
    Requirement (M09, declared status: implemented in part, validation pending): "Retention setup exists"; "A configured retention period determines which older transactions expire […] the current 90-day default is a setting to review".
    In plain words: transactions older than a configured period must be deleted automatically; the current default declared is 90 days.    		 At start-up the system sets up, in the database, the automatic deletion of transactions older than the configured period. The configured period is 180 days; 90 days are used only when the configuration is missing. The declared default (90 days) does not match: 180 days are configured, also in the sample copy of the database. Deletion is based on a date (BeginDateTime) that data loading does not produce: none of the 3,000 records in the sample copy contains it (they all have a different date, TransactionDateTime). With this data, no record is ever deleted. If automatic deletion has already been set up before, a change of period is not applied. In JSON files, dates are recognised as dates only when written in a special format; otherwise they stay text. There is no screen to manage retention. The log of loaded files is never cleaned up. 🟡

    M10 Release readiness#

    Item Implemented R – missing vs. requirement Q – quality assessment Result
    Application code and documentation present
    Requirement (M10, declared status: in progress): "Core application code and documentation are present."
    In plain words: the application code and its documentation must exist; the document lists as still to complete testing, user feedback, activity logging, security review, deployment and guides (including videos).    		 The code includes the server (organised in several parts), the data-loading program and the web interface. The documentation includes 14 documents (among them installation, deployment, user manual, testing and change history), a quick guide to the similarity analysis, the description of the anti-fraud services and a README file. Present There are no automated tests. There is no automated build and release process, and no files for setting up the infrastructure. There is no log of user activity and no structured event logging. The server accepts requests from the browser only from local development addresses; there is no enforced secure connection (HTTPS) and no limit on the number of requests. There are no videos. ✅

    Roadmap and further development – statements about what already exists#

    Item Implemented R – missing vs. requirement Q – quality assessment Result
    R01
    Requirement (R01, declared status: planned extension): "Database setup materials exist; guided provisioning remains future work."
    In plain words: materials to set up the database already exist; a guided installation is future work.    		 Scripts to create permissions, the administrator role and rules, with the full list of permissions; sample copy of the database (10 collections plus 2 old copies). Present There is no guided installation and no licence management: consistent with the "planned" status. ✅
    R02
    Requirement (R02, declared status: planned): "Existing user permissions do not establish a complete multi-customer model."
    In plain words: the current permissions are not enough to serve several separate customers; customer separation is future work.    		 Permissions and roles are assigned to individual users; the application connects to a single database. Present There is no handling of separate customers and no per-customer branding: consistent with the "planned" status. ✅
    R03
    Requirement (R03, SSO planned): "Email-based forgot-password capability is already present and belongs in MVP validation."
    In plain words: password recovery by email already exists; sign-in with company credentials (SSO) is future work.    		 See "Email password recovery". Present There is no single sign-on with company credentials (SSO): consistent with the "planned" status. ✅
    R04
    Requirement (R04, planned extension): "Core reporting is implemented. Linked reports and additional charting are planned extensions."
